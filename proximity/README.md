# proximity/ — FlUni, the student app, and its test harness

One Xcode project (generated by XcodeGen from `project.yml`), two apps that share the same code:

| Folder | What | Built into |
|---|---|---|
| `Core/` | Sensing (Bluetooth beacon, peer link, UWB, GPS), fusion, exposure, risk. No SwiftUI. | both |
| `SharedUI/` | Theme (Lisa's campfire palette), Map tab, developer view, notification delegate | both |
| `FlUni/` | **FlUni**, the student app (`com.fluni.app`): Today / Map / Me, onboarding, assets | FlUni |
| `Harness/` | **FluniProx**, the test harness (`com.fluni.proxtest`): developer view first, obeys test launch arguments | FluniProx |
| `Tests/` | Unit tests (run inside the harness) | — |

The harness exists so every link/stress test exercises exactly the code that ships. FlUni ignores test
launch arguments. Plan: move `Core/` into a Swift package later (keep it free of UI code until then).

## What the student sees

- **Onboarding** (first launch only): what the app does, what is and isn't shared, then a "Turn on"
  step that explains Bluetooth, Nearby Interaction, Location and Notifications and only then starts
  the radios (so the system prompts come with context). Completion is stored in UserDefaults
  (`hasOnboarded`).
- **Today**: a calm status card (all clear / someone nearby may be contagious / close contact) with
  plain-language advice, close-contact minutes out of 15, and a count of Fluni phones nearby (never
  IDs or per-person distances). A sheet explains how it works and what is shared.
- **Map**: the heat map web page (user view, `?embed=app`). The gear button sets its address.
- **Me**: "I feel fine" / "I have symptoms" / "I tested positive" (with a confirmation), what each
  shares, and when the status was set. "Developer tools" at the bottom (Debug builds only; a Release FlUni has no such row) opens the **Developer** screen:
  per-peer rows with sensor chips and Details, demo speed, source toggles, reset, radio status.

**Test launches skip onboarding.** If any of `-risk -speed -sources -encryption -inviteTimeout -rotate
-riskAfter -skipOnboarding` is on the command line (as the scripts in `tools/` and `stress.py` pass
them), the app starts the radios immediately and the `[fluni]` log lines are unchanged. The unit-test
host (`XCTestConfigurationFilePath`) never starts radios. Default speed is real time; demos pass `-speed 60`.

**Design.** The "campfire" palette (sage, sun, ember, fire, paper, ink) and the hand-drawn tissue
illustration are by Lisa Zheng ([@lisaazheng](https://github.com/lisaazheng)), from the heat map design
pass (`heatmap/assets/people/tissue.png`); the app icon is derived from that tissue. Tokens are in
`Theme.swift`. The app is forced to light mode (the palette is only defined and contrast-checked on warm
paper). Type is the system rounded font so Dynamic Type works; Hanken Grotesk (the web font) isn't
bundled because its variable weights can't be verified here without running the app.
Credits: hand-drawn containers (`heatmap/assets/containers`): Lisa Zheng.

## How it works

Each phone advertises a **random ID that changes every 15 min**, a **3-level risk** (healthy, possibly sick,
contagious), the **days since its user's symptom onset or positive test**, and its **own risk score** (see "Shared
risk" below). Nothing else is broadcast. All matching happens on the phone,
with no server. (Decision 2026-10-17: live alerts beat retrospective matching for the demo; see
WORKSTREAMS.md.)

| Channel | What it carries | Distance quality |
|---|---|---|
| **Bluetooth LE** beacon | Packed into one 128-bit service UUID: `FLU2`, status byte (risk in bits 0-1, days since onset 0-14 in bits 2-5, 15 = unknown), score byte round(255·√p), 10-byte ID. Older builds' `FLU1` (risk, 11-byte ID) is still accepted, with score and days unknown. Needs no connection. | RSSI, ±(70 % of the distance + 0.3 m); ±(40 % + 0.3 m) once calibrated against UWB |
| **Bluetooth LE, background** (FlUni only) | The same 16 bytes, read over GATT: fixed service `142C3940-E33C-4D62-BE25-1C4A883EE402`, read-only characteristic `2F02CED2-60A0-41AC-A335-07D1603177E4`. Nothing more than the advert carries. | RSSI of the advert |
| **Peer link** (MultipeerConnectivity, encrypted) | hello (ID + risk + UWB capability), UWB tokens; GPS fixes **only in the harness**. New random link name on every ID rotation; every message size-capped (4 KB), rate-limited and validated; max 8 peers. The link's risk is never used (Bluetooth's is), and a hello ID counts only if Bluetooth heard it in the last 30 s | — |
| **UWB** (Nearby Interaction, U1 chip) | needs tokens swapped over the peer link; keeps ranging through link drops (30 s grace); extended distance when both phones have the U2 chip | ~10 cm |
| **GPS** | FlUni: your own fix, used **only on your phone** (building warnings); never sent. Harness: also sent to the linked phone for GPS ranging tests | 5–20 m, poor indoors |

**Fusion** (`Fusion.swift`): fresh readings are averaged, each weighted by 1/σ². UWB dominates when
present; Bluetooth and GPS take over when it drops out. A UWB reading keeps full weight for 3 s, then
stays usable to 6 s with its σ growing 1 m/s, so one dropped frame doesn't snap the distance to Bluetooth. While UWB is live, it **calibrates the
Bluetooth model** for that phone pair, so Bluetooth-only ranging improves afterwards. The result is
P(within 6 ft), not a yes/no.

**Background** (FlUni only; `BLEBeacon.swift`, `BeaconGATT.swift`, `BackgroundAccrual.swift`). In the
background iOS hides the payload UUID (it moves to the "overflow" area, matched only by scans that name
it). So FlUni also advertises a fixed service UUID and serves the payload from a GATT characteristic. A
second scanner names that UUID (required in the background; also catches backgrounded phones while FlUni
is open). When an advert has the fixed UUID but no payload, it connects, reads the 16 bytes, keeps the
advert's RSSI and disconnects: at most once per 20 s per peripheral and 3 connections at a time.
Bluetooth state restoration (`fluni.advertiser`, `fluni.scanner`) lets iOS relaunch FlUni in the
background for a Bluetooth event after the *system* ended it, not after the user swiped it away
([TN3115](https://developer.apple.com/documentation/technotes/tn3115-bluetooth-state-restoration-app-relaunch-rules)).
UWB and the peer link are foreground-only.

**Off screen** (`Core/OffScreenRanging.swift`). In the background iOS coalesces a phone's repeated adverts
into one discovery, and two locked iPhones rarely discover each other at all. An open GATT connection survives
the lock, though, and each RSSI read on it wakes FlUni. So the scanner keeps a link open to the 4 nearest FlUni
phones (opened while either phone is in the foreground, or after a background read; a full table swaps its
weakest link for a phone 6 dB stronger), reads RSSI every 2 s and re-reads the payload every 30 s (ID rotation,
status). A dropped link is re-requested for 10 min; iOS completes it when the phone is back in range. Polled
samples count only when no advert for that ID arrived in 3 s, so foreground ranging is unchanged. A BLE median
over n < 4 samples gets sigma × sqrt(4/n), so P(≤ 6 ft) stays honest without UWB. The links carry the same 16
bytes as the advert; FlUni never links a peer's old and new IDs. Log lines: `hold open|poll|lost|reconnected …`.
**Always location** (`Core/BackgroundLocation.swift`). With Always, FlUni keeps standard location updates on
off screen (3 km accuracy, 500 m filter: cell and Wi-Fi, no GPS radio; blue location indicator shown), which keeps
it running while locked: the 1 s tick, the link polls and a Bluetooth scan restart every 10 s carry on. Coarse
fixes are never used for walk-in warnings (geofences do that). Off while paused or after Delete my data; without
Always nothing changes. The Always ask is the card on Today after onboarding (and Settings).
After a swipe-away nothing runs until iOS relaunches FlUni for a location event (significant change, visit or
building geofence, Always permission only); FlUni then restarts Bluetooth detection. A phone that is powered
off cannot be detected by anything.

Exposure in the background comes from sightings rather than the 1 s timer: each peer remembers when it
was last credited, and a re-sighting within 5 min credits the whole gap at its latest P(≤ 6 ft); a
longer gap credits nothing. The timer goes through the same per-peer bookkeeping, so no second counts
twice. Log lines: `bg launch`, `bg restore …`, `bg gatt read …`, `bg gatt served …`, `bg credit …`.

| | Nearby alerts | Building warnings |
|---|---|---|
| FlUni open | yes, every second | yes |
| In the background | yes, via Bluetooth, less often (when iOS delivers a sighting); a phone with FlUni open sees it best | yes (geofences) |
| Ended by iOS (memory) | yes: iOS keeps advertising/scanning and relaunches FlUni on a Bluetooth event | yes (relaunched on region entry) |
| Swiped away by the user | no, until FlUni is opened again | yes (region monitoring still relaunches it) |

Two phones that are both in the background find each other only now and then (iOS mostly matches
overflow adverts while the scanning phone's screen is on).

**Exposure** (`Exposure.swift`): minutes += dt × P(≤ 6 ft) × weight, where weight is 1 for
contagious and 0.5 for possibly sick. The app shows a heads-up as soon as a risky phone is probably
within 6 ft, and a **close-contact alert with advice at 15 cumulative minutes** (the CDC rule).
Demo speed (1×, 10× or 60×) scales time, so 60× gets there in 15 seconds. In Debug builds the speed is saved across launches.

**Risk estimate** (`RiskEstimate.swift`, "This phone's estimate"): Rio's exposure formula (Baker et al. 2021) as
`model/infer.js` computes it, with what a phone knows. Each tick, a risky peer with a fused distance d ≤ 10 m
(Bluetooth range; no estimate or coarse GPS alone adds nothing) adds the unit dose
q·B·(dt/3600)·(1/(30·max(d, 0.3)²·o) + 1/(V·loss)): q 10 quanta/h (1.5 in a dorm room), B 0.5 m³/h, V and
ventilation of **this phone's room**, loss = ach + 0.3 settling + virus decay at the January indoor humidity
(Magnus); outdoors o = 5 and no room term. The room comes from this phone's own GPS fix (`RoomContext`, never sent):
inside a building, that building's representative room from `FlUni/Resources/building_rooms.csv` (the median-volume
room of the sim run's `map/rooms.csv`, made by `tools/make_building_rooms.py`); at an outdoor place, or with the whole
accuracy circle clear of every building, outdoors; otherwise (no fix, stale, near an edge, the harness) the default
room 50 m² × 2.7 m at 2 ach. Each contact's dose is weighted by the peer's **stage**: infer.js `stageFactor` of the
days since onset the peer broadcasts while it reports symptoms or a positive test, else the illness average 0.352.
`ExposureTracker` sums Σ stage·dose per rotating peer ID over the 24 h window, with the ID's highest evidence level s
seen in the window. Then p = 0.02, and per ID p ← p + (1 − p)·s·(1 − e^(−Σ stage·dose)). ContactGuard's rules limit
the dose as they limit minutes. The constants come from infer.js `DEFAULTS` and are checked against it by
`Tests/CrossCheckTests.swift` and `Tests/ShareRiskTests.swift` (golden vectors from the real infer.js:
`node Tests/Fixtures/xcheck/make_golden.mjs`; the shared-risk, stage and room scenarios match within 1e-12).
What the phone can't do: walls (which room the peer is in), second-hand risk and look-back after a report (need
everyone's contacts), recovery (24 h window instead), negative tests of others. One person seen under two rotating
IDs counts as two sources, a slight over-estimate.

**Shared risk** (product owner, 2026-10-17). Each phone broadcasts its **own score**
`ownScore = max(liveRisk, status floor)` (floor 0.97 after a reported positive test, 0.6 after reporting symptoms,
0 otherwise; `ProximityModel.ownScore`). The beacon carries the previous tick's value (`OwnScoreLag`): a phone's
estimate already uses its peers' scores, so the one-tick lag keeps two phones from feeding each other's current value
back. Per peer, **s = max(status s, max(0, P_peer − 0.02))** with P_peer its latest broadcast score; an old FLU1
beacon (no score) gives the status s. The score affects the probability only: the **"nearby" heads-up and the
close-contact minutes still count only peers whose status is possibly sick or contagious**. ContactGuard ignores a
score that is implausible for its status (healthy but ≥ 0.9, or moving more than 0.5 within 1 min), counts a
"healthy" ID whose score alone gives s ≥ 0.6 toward the burst rule, and keeps at most the 2 dose sources that add
most. **Nobody sees anyone else's score or days in FlUni** (not in Recent contacts, the developer list or the logs;
`ScoreIsNeverShownTests`), but they travel in plain Bluetooth, so a BLE scanner app can read them: hidden, not
secret (`RISKS.md`). The user's own status floor lasts exactly as long as their status (`myRisk`): it ends when
the self-report goes back to healthy (Core/SelfReport.swift). `ProximityModel.selfStatusOverridesRisk` is true
while it applies, and the risk card shows `ownScore`, so a reported-positive user never reads "Low".

**Live on screen.** `ProximityModel.liveRisk` (@Published) is p, recomputed on every 1 s tick while a risky
peer's dose accrues (per second, not per minute), on return to the foreground (the background gap is credited
at once) and when the 24 h window drops old dose. Today's risk card leads with it, always, as
`RiskEstimate.liveText` (one decimal below 10%, e.g. 2.0% → 2.3%; whole percent above), animated with
`.numericText` unless Reduce Motion is on. In Debug builds with a "Play as" persona, the campus model's
number is an extra line under it, never in its place. `percentText` (whole percent) stays the text shared
with the heat map. Debug only: `-demoPeer contagious@0.5` (or `possible@2`) puts a pretend peer that far away,
no radios needed, so the simulator shows p climbing (add `-speed 60` to see it move every second).

**Relaunch** (`Core/RiskState.swift`): the estimate survives iOS ending and relaunching FlUni. The exposure tracker
(24 h per-minute buckets, per-ID dose with s and stage, minutes, alert level) and the alert gate (when each alert was
last notified) are saved to `Application Support/risk-state.json` on the phone only (file protection until first
unlock, atomic writes): on every alert-level change, on going to the background, and at most every 30 s while the
number changes. On launch the 24 h window moves on by the real time since the save and nothing is credited for that
gap; a corrupt or future-dated file (beyond 60 s of clock skew) is dropped and logged, and FlUni starts at the prior.
Test launches and the unit-test host never read or write it (Debug: `-keepRiskState YES` opts a test launch in, e.g.
with `-demoPeer`). Reset exposure and Delete my data remove it.

**Clock.** Students see live time only: the device's local weekday and time of day mapped onto the run
(`Core/LiveClock.swift`, rule in `docs/building-heat-format.md`), recomputed every 15 s and on any system clock,
time zone or date change. The Map tab says "Now · updated 4:30 PM". In Debug builds, Me > Developer tools > Demo
controls > Demo override replaces it with a chosen sim time (persona, run, follow, "Pretend I'm at…"), and Today and
Map show a "Demo time" badge while it is on.

The **Map tab** loads the heat map workstream's page (`heatmap/`) over the local network
rather than copying it:

```
cd fluni && python3 -m http.server 8000      # on the laptop
# in the app, Map tab, gear button: http://<laptop>.local:8000/heatmap/?embed=app
```

## Run

Requirements: Xcode 26+, [XcodeGen](https://github.com/yonaskolb/XcodeGen) (`brew install xcodegen`),
and two U1/U2 iPhones (iPhone 11 or later, not SE). The phones need Developer Mode on and must be
paired with the Mac (tap Trust).

```
cd proximity
FLUNI_TEAM=<your team id> xcodegen generate      # team id: Xcode → Settings → Accounts
open FluniProx.xcodeproj                           # or use the script below
```

Unit tests (fusion + exposure logic; no radios needed):

```
xcodebuild test -project FluniProx.xcodeproj -scheme FluniProx \
  -destination 'platform=iOS Simulator,name=<any iPhone sim>' CODE_SIGNING_ALLOWED=NO
```

**Two-phone test** (builds, installs, launches both phones and streams their `[fluni]` logs):

```
FLUNI_TEAM=<team> tools/pair_test.sh fused 60    # A contagious; B (and C) listen on UWB+BLE+GPS
tools/pair_test.sh uwb|ble|gps|control           # one channel only, or nobody sick (expect no alert)
SKIP_BUILD=1 tools/pair_test.sh ble              # reuse the installed build
tools/doctor.sh                                  # read-only check: phones, team, simulators, GitHub
tools/sim_test.sh together                       # two iPhone simulators (needs a standard iOS runtime)
tools/serve_heatmap.sh                           # serves the repo root; prints the phone URL
```

The scripts are bash and exit non-zero with a reason if a phone is locked, untrusted, unpaired or has
Developer Mode off. `sim_test.sh` never uses iPhone Duo; if no standard runtime exists, run
`xcodebuild -downloadPlatform iOS`.

With phones side by side at 60×, B should log `ALERT nearby` within seconds, then
`ALERT closeContact` at about 15 s. The `control` case should never alert. To test "apart → no alert",
run `fused` with the phones in different rooms.

Launch arguments (also usable from Xcode's scheme): `-risk none|possible|contagious`, `-speed 60`,
`-sources UWB,BLE,GPS`, `-heatmapURL http://…`, `-skipOnboarding`; FlUni Debug also takes `-demoPeer contagious@0.5`.

**Link and UWB uptime.** One MPC handshake at a time per phone (field logs: concurrent handshakes
mostly hung), 6 s invite timeout. No discovery restarts, and an MPC browser is never stopped: stopping one
crashes the app now and then inside Apple's code (`_BrowserCancel` SIGTRAP, see `Core/BrowserLedger.swift`).
Retired browsers are parked until iOS backgrounds the app. The app logs
`[fluni] link metric handshake=…` per link and `link metric uwb_resume gap=… after_drop=…` when UWB comes
back; `tools/stress.py` reports them (`handshake_med`, `link_failed`, `uwb_gap_max`, `uwb_after_drop_max`).

## Limits

- Best in the foreground: in the background only Bluetooth works (no UWB, no peer link), sightings are
  sparser, and two backgrounded phones rarely see each other. The app keeps the screen on while open.
- Free Apple developer teams sign builds for 7 days; reinstall after that.
- Privacy: in a room with just two people, the risk bit identifies the sick one. Acceptable for the
  demo, but it needs a fix (anonymity threshold or server-side matching) before real use.

## Accessibility & copy

Conventions for anything user-facing in `FlUni/` (the Developer screen is exempt from the plain-English rule).

- **Tone:** calm, specific, actionable; short sentences. No jargon outside Developer: say "precise distance
  sensing", not UWB; "weighted minutes" for close-contact time; "exposure dose" only in "How is this calculated?", where it
  is explained.
- **Terms, used the same everywhere:** "close contact", "someone with symptoms" / "someone who tested
  positive", "detection" (on/off/paused), "FlUni" (exact capitalisation). The three shared statuses are always
  "healthy", "possibly sick", "contagious".
- **Buttons are verbs** ("Set my status to healthy", "Resume detection"). Alert titles say what happened.
- **VoiceOver:** every icon-only control has a label; decorative icons are `accessibilityHidden`; related text
  is combined into one element; headings carry `.isHeader`; buttons that open something have a hint.
  Progress reads as a sentence ("Close-contact time, 7 of 15 minutes").
- **Dynamic Type:** no fixed heights. Rows that would truncate use `ViewThatFits` (side by side, else stacked);
  icon sizes use `@ScaledMetric`; onboarding scrolls instead of clipping.
- **Tap targets:** at least 44 x 44 pt (`minHeight: 44`).
- **Contrast:** body text 4.5:1, large text and icons 3:1. The computed ratios for every pair are in the
  comment at the top of `Theme.swift`. Use ink / ink-2 / fire-ink on tints; ink-3 only on paper or surface-2;
  never fire, ember or sage as text or as the only mark of a progress bar.
- **Risk tiers** colour the risk card via `RiskEstimate.band` (sage / sun / fire); the band is also stated in
  words ("Low.", "Elevated.", "High.") so colour is never the only cue.
- **Reduce Motion:** animations check `accessibilityReduceMotion` and switch to instant changes.
